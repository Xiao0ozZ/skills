# 工作流维护与自检

本文件只用于维护 `workdesk` 源库。默认只改源库草案，不发布、不安装、不同步运行目录。

## 使用方式

Use this file only when editing or auditing the workflow skill itself.

- For `继续优化` or skill cleanup: read sections 1 to 5, then edit source-library files only.
- For deciding whether to write a new rule: read section 2.
- For final validation: use sections 4, 5 and 6.
- Do not publish, install or sync unless the user explicitly asks.

## 目录

- `1. Skill 定位`
- `2. 写入判断`
- `3. 文件分工`
- `4. Progressive Disclosure 自检`
- `4.1 好用性自检`
- `5. 通用性自检`
- `6. 输出自检`

## 1. Skill 定位

这个 Skill 是个人管理工具：

- 第一层：个人工作习惯、思考方法、判断方式、沟通表达、推进和收口。
- 第二层：交付物方法，如文档、PRD、PPT、纪要、验收、交接、复盘。
- 第三层：外部上下文边界、来源读取和资料整理。
- 第四层：知识库记录、模板记录、工作流自优化。

不要把它维护成单个工作来源说明书、文件索引合集、Obsidian 全文资料库、业务规则库或临时偏好记录。

## 2. 写入判断

可以直接写入源库草案：

- 稳定复用的工作习惯。
- 通用判断框架。
- 通用交付模板。
- 可防止重复错误的检查清单。
- 自然语言触发规则。
- 跨场景适用的写作、评审、收口、知识记录方法。
- 低风险措辞、目录和引用修正。

必须先确认：

- 改变文件写入、Obsidian 写入、正式资料写回或发布策略。
- 固化业务规则。
- 新增、移动或重命名 Obsidian 结构。
- 删除或重命名已有 reference、asset、script。
- 改变触发范围或默认输出深度。

不能写入：

- 未确认事实。
- 单次聊天内容。
- 临时偏好。
- 客户敏感资料、账号、密钥、完整转写稿。
- 已被否定的想法，除非作为明确反例且有复用价值。

## 3. 文件分工

- `SKILL.md`：只放定位、触发、加载路线、确认门槛、文件/记忆规则和维护入口。
- `references/00-工作模式与个人方法.md`：个人方法论、工作模式、输出形态、推进、沟通、收口。
- `references/10-任务路由与上下文边界.md`：短触发、任务分类、是否需要外部上下文、最小读取顺序和确认门槛。
- `references/20-事项接入与资料整理.md`：新事项接手、杂乱资料整理、主入口草案、目录归类和确认流程。
- `references/30-交付总览.md`：交付模块 router，只做窄模块选择。
- `references/31-需求分析与PRD.md`：资料阶段、需求接手、范围、PRD、字段状态和验收。
- `references/32-方案PPT与模板.md`：方案、PPT、母版、页面展示、附件页和模板资产。
- `references/33-会议总结与知识沉淀.md`：会议、总结、Obsidian 知识记录和双链。
- `references/34-同步交接与复用.md`：文档/来源/实现同步、工程交接、迁移复用和自优化候选。
- `references/35-HTML原型与页面规范.md`：HTML 原型页、页面骨架、视觉语言、状态规范和 prototype-only 交付规则。
- `references/90-工作流维护与自检.md`：本文件，约束 skill 自身怎么维护。
- `assets/`：可复用模板和受保护母版资产；HTML 原型母版放在 `assets/prototype-templates/`，只作为输出基座，不把完整源码塞进 reference。
- `evals/trigger-evals.json`：触发、路由、工作模式、上下文边界和输出深度的回归样例。
- `scripts/`：稳定重复、需要确定性的检查或发布脚本。`check_workflow_skill_health.ps1` 是只读健康检查；发布脚本只在用户明确要求发布时运行。

## 4. Progressive Disclosure 自检

每次优化后检查：

1. `description` 是否能触发常见请求，但没有塞太多细节。
2. `SKILL.md` 是否仍像入口调度器，而不是完整资料库。
3. 细节是否已经下沉到最合适的 reference。
4. reference 是否能从 `SKILL.md` 一跳找到。
5. 是否有重复规则分散在多个文件里。
6. 是否引入了只对某个来源有效的事实。
7. 是否把业务规则写进了通用方法层。
8. 是否新增了脚本可以解决的机械检查，却只写成人工提醒。
9. `evals/trigger-evals.json` 是否覆盖快答、工作稿、正式交付、上下文边界、原型页、知识沉淀和 Skill 维护的典型样例。

`description` 是常驻触发信息，只放定位、主要能力和高频触发词。不要把详细流程、具体目录、长来源清单或一次性优化结论写进 `description`。

轻量阈值：

- `SKILL.md` 原则上保持在 120 行以内；超过时优先下沉到 reference。
- `description` 原则上保持在约 100 个英文分词以内；新增触发词时优先合并同类词，不展开长清单。
- `description` 优先使用“文件/来源/上下文/当前材料”这类泛触发；具体来源名不要写进 Skill。
- 单个 reference 超过 100 行时，顶部必须有 `## 目录`；超过 500 行时必须优先拆成 router + narrow module，不要默认整篇加载。
- 新增规则必须减少未来操作成本；如果只是“看起来更完整”，不要写入。

## 4.1 好用性自检

每次优化后额外检查：

1. 用户是否可以用自然语言直接触发，不需要记命令。
2. 低风险任务是否能先给可用版本，而不是先问一串问题。
3. 输出是否默认短、直接、能继续改。
4. 待确认项是否只保留会改变事实、方向、写回或长期记忆的问题。
5. 规则是否让下一次更省事，而不是增加阅读负担。

## 5. 通用性自检

每次优化后检查：

- 不写死本机绝对路径、个人目录或工作目录。
- 不写具体来源目录。
- 不承载单一来源的大型规则库；大规则放到对应来源，只在该上下文读取。
- 不默认使用 workflow-agent。
- 不默认所有任务都进入外部上下文。
- 不自动发布或同步运行目录。
- 发布脚本必须支持 DryRun 或备份，避免误覆盖安装目录。
- 不自动写 Obsidian。
- Obsidian 新建或更新前必须先给路径、摘要和双链建议，等用户确认。
- 不要求用户记命令；自然语言也能触发。

## 6. 输出自检

维护完成后，最终回复只说明：

1. 改了哪些源库文件。
2. 为什么改。
3. 跑了什么检查。
4. 是否没有发布。
5. 还剩哪些风险或建议。

不要输出长篇维护过程。不要把旧评价记录复述给用户。

维护后优先运行 `scripts/check_workflow_skill_health.ps1` 做只读检查。脚本失败时先修源库草案，不要发布后再修。
