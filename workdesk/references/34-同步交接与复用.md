# 同步交接与复用

## 使用方式

Use this internal module for document/source synchronization, handoff, reuse across contexts and workflow-improvement candidate detection.

- Requirement or solution changes: read section 1.
- Real code/API/development handoff: read sections 1.1 and 1.2.
- Reuse to another domain or work context: read section 1.3.
- Skill self-optimization candidates: read section 2, then use `90-工作流维护与自检.md`.

## 1. 文档 / 来源 / 实现同步判断

需求或方案进入正式交付、用户明确要求落文件，或变化会影响真实代码/接口/正式资料时，必须判断是否影响以下资料：

| 资料 | 何时同步 |
| --- | --- |
| PRD | 规则、字段、状态、流程、权限、异常、页面行为发生变化 |
| 原型 | 用户可见入口、列表、详情、弹窗、按钮、状态标签、示例数据发生变化 |
| 工作知识库 | 出现长期有效的业务规则、背景说明或操作约定 |
| 正式文档版本记录 / 工作知识库 | 出现最终确认、会影响后续判断的跨模块规则 |
| 代码 / 接口 | 用户要求真实实现，或交付物会影响真实页面、API、权限、状态管理 |
| Obsidian | 出现可复用的方法、模板、套路、复盘或经验 |
| Skill | 出现稳定可复用的工作流、检查清单、加载规则或重复失败模式 |

快答和工作稿只列必要同步候选，不展开完整写回流程。正式交付默认先分析、给结论、列同步项，再问是否落文件。不要把用户说“直接写”理解成可以推翻已确认来源规则。

### 1.1 PRD / 原型 / 真实代码三轨规则

- 如果同模块已有原型，默认把原型列为同步候选；但确认写文件前不直接改原型。
- 如果用户明确说“只做原型 / 先出 HTML 页面”，默认按 `35-HTML原型与页面规范.md` 输出，同步统一页面骨架和状态规范，不假装已经接入真实实现。
- 如果用户明确说“只要 PRD”，不改原型，但 PRD 必须写清页面行为，便于后续补原型。
- 如果用户明确说“只要原型”，也要补最小页面说明：页面目标、角色、结构、关键字段/按钮、状态/弹窗和待确认项。
- 如果没有对应原型目录，交付以 PRD 和页面行为说明为主，不凭空新建一套 HTML 原型。
- 新场景如果没有单独品牌/终端规范，默认沿用同一套后台原型风格、主框架和状态表达，不每次重造视觉语言。
- 如果用户直接要求真实页面、真实接口或 API 接入，优先读取真实代码、路由、组件、状态管理、API client、权限和样式体系，不强制补 HTML 原型。
- 无论是否有原型，涉及页面行为时都要写清字段、按钮、状态、弹窗、校验、权限、异常提示、列表/详情展示和空态/加载/失败状态。
- 真实代码与 PRD、原型或已确认资料冲突时，先指出冲突并给同步方案，不直接以代码现状覆盖来源规则。

## 1.2 工程开发与交接收口

进入真实工程开发、接口联调、页面改造、修 bug 或“接着开发”时，必须把工作做成可接手状态。

开发前先确认：

- 当前代码目录和运行方式。
- 相关 PRD、原型、接口、权限、数据模型和测试命令。
- 改动范围：前端、后端、数据库、配置、脚本、文档。
- 验证方式：测试、构建、截图、接口调用或人工检查。

开发后默认输出：

1. 改了什么。
2. 为什么这样改。
3. 验证结果。
4. 文档同步项：是否需要更新任务台账、技术文档、AI handoff、README、PRD、原型、版本记录或知识库。
5. 未完成和风险。
6. 下一步接手入口。

如果已有任务台账、技术开发指南或 AI handoff，完成实质开发后默认列出同步建议。只有用户明确要求或来源规则允许时，才直接写回这些文件。

如果本轮创建或修改了 PRD、Word/Markdown 文档、方案说明、PPT/汇报材料、会议纪要、交接文档、客户说明或其他文案类正式文件，默认检查该文件自身的版本记录是否同步更新，并确认版本记录位于标题/封面之后、正文之前；没有专门变更台账时，也不能省掉文件自身的版本记录。

## 1.3 迁移复用判断

当用户问“能不能复用到另一个场景”“类似业务怎么做”“把这套能力迁移到新领域”时，先做抽象，不复制来源事实。

输出分四类：

1. 可复用能力：流程、状态、权限、字段、交互、验收、异常处理。
2. 需要替换的领域概念：把原场景的对象、角色、动作、资源、风险和计费单位替换成目标领域语义。
3. 不能直接复用的部分：客户事实、业务限制、金额规则、合同承诺、技术约束、历史数据、上线节奏。
4. 固定检查项：用户是谁、对象是什么、资源何时锁定、状态如何流转、资金如何处理、历史如何保留、异常谁处理、页面和接口如何承载。

迁移复用结果默认作为分析结论或 Obsidian 知识候选，不直接写入目标来源或 Skill。只有目标上下文确认后，才写入对应资料。

## 2. Skill 自动维护判断

本模块只负责交付、知识记录和写回场景中的候选识别。具体写入判断、文件分工、progressive disclosure、通用性检查和发布策略统一读取 `90-工作流维护与自检.md`。

做完实质性工作后，只有发现可重复使用、能避免再次出错、能形成检查清单、模板或触发规则的内容，才输出短的 `可优化/可写入知识库` 建议；没有稳定复用价值时保持安静。

来源事实留在来源资料、PRD、版本记录或工作知识库；通用方法才进入个人管理工具；个人知识进入 Obsidian 前必须先给路径、摘要和双链建议并等待确认。
