# 需求分析与PRD

## 使用方式

Use this internal module for source-stage judgment, requirement intake, scope analysis, field/status logic, PRD rules and acceptance design.

- Source and history judgment: read section 1.
- Requirement intake and scope judgment: read section 2.
- Field/status/PRD work: read section 3.
- Acceptance/test design: read section 4.
- If the task is prototype-only page delivery, use `35-HTML原型与页面规范.md` as the page-expression module.
- If the task is only communication, summary or planning, prefer `00-工作模式与个人方法.md`.
- If external facts or files are required, route through `10-任务路由与上下文边界.md` first.

## 1. 资料阶段

先判断是否真的需要读资料。只需要思考、表达、推进或复盘时，先用个人方法层；需要事实依据、文件内容或写回时，再按最小范围读取，不要一上来扫全目录。

优先顺序：

1. 用户当前提供的材料、当前对话和明确目标。
2. 用户指定的目标文档、表格、截图、链接或文件夹。
3. 当前有效的 README、目录说明、版本记录或工作说明。
4. 直接相关的 PRD、原型、代码、接口、会议纪要、正式文档、模板或历史记录。

只要来源阶段不清楚，先标注它是“当前有效、历史记录、规划设想、评审意见、实现现状、用户口头确认、推断”中的哪一种。

### 1.1 资料角色

进入外部上下文后，先判断资料角色，不要把所有文件都当成同一种事实来源。

| 资料 | 默认角色 | 使用方式 |
| --- | --- | --- |
| PRD / 正式产品文档 | 交付规则 | 用于开发交底和功能规则判断；冲突时仍要看最新确认和文档版本记录。 |
| 已确认记录 / 文档版本记录 | 当前有效决定或修改历史 | 优先沿用文档自身版本记录；不默认新建单独台账。 |
| 业务知识库 / 工作知识库 | 背景和长期规则 | 可支撑问答和分析；与最新决定冲突时先指出。 |
| HTML / Figma / Axure 原型 | 页面表达 | 用来确认入口、字段、按钮、状态和交互，不自动覆盖后端规则。 |
| 真实代码 / API | 实现现状 | 做真实页面/API 时必须读取；代码与 PRD 冲突时先给同步建议。 |
| 历史归档 / 旧版本 | 追溯来源 | 不作为当前规则，除非用户明确要求查历史或恢复旧版本。 |
| 评审 / 投标 / 可研 / 总体方案 | 承诺、规划或说明 | 不等于已经开发、验收或最终定版。 |

回答资料恢复型问题时，默认写清依据阶段：承诺、评审整改、规划、原型表达、当前实现，还是推断。

## 2. 需求分析

遇到新需求、方案设计、PRD、原型、评审或规划任务时，先判断它是日常方法问题、通用交付问题，还是需要具体来源的问题。不是具体来源问题时，不追问来源，先按个人方法层推进。

分析顺序：

1. 目标：要解决什么问题，谁受益。
2. 场景：用户在什么情况下做什么动作。
3. 对象：被管理、被申请、被支付、被审批、被记录的对象是什么。
4. 状态：对象生命周期如何变化。
5. 权限：谁可以看、改、审、撤、导出、删除。
6. 规则：金额、时间、数量、范围、异常、边界条件。
7. 数据：新增哪些字段，哪些字段可配置，哪些字段需要历史保留。
8. 交互：入口、列表、详情、弹窗、按钮、空态、错误提示。
9. 验收：什么情况算完成，什么情况算不支持。

不要把“看起来完整”当作目标。先把主流程、异常流程、权限和状态讲清楚。

范围判断：

| 类型 | 判断 | 输出方式 |
| --- | --- | --- |
| 当前已确认 | 已有正式资料、决定或实现支撑 | 直接按当前规则回答或设计 |
| 本期必须做 | 不做会导致主流程不完整、状态错误、资金错误、资源占用错误或权限越权 | 写入交付物，并列同步项 |
| 本期人工兜底 | 主流程可运行，但异常需要人工处理或线下流程 | 写清角色、入口、记录和提示 |
| 本期不做 | 超出现有模型、依赖大能力或会扩大工作量 | 明确不支持，不做假完整 |
| 未来规划 | 有价值但依赖后续能力、配置中心、审批、深度对账、统一排程等 | 单独列未来能力，不写成当前支持 |
| 当前未定义 | 资料和用户确认都没有最终规则，且影响核心判断 | 列决策点、影响和推荐方向 |

### 2.1 输出结构

需求分析默认输出：

1. 结论：该需求应该如何处理。
2. 影响：影响哪些资料、角色、流程、字段、状态、原型、代码、会议或交付物。
3. 漏洞：缺什么关键规则，哪里会误解。
4. 推荐方案：主流程、异常流程、权限、状态、数据。
5. 待确认：只列会改变设计的问题。
6. 同步建议：是否需要同步 PRD、原型、代码、测试用例、会议结论、版本记录或知识库。

PRD 草稿默认结构：

1. 背景与目标。
2. 用户与场景。
3. 范围：本期做 / 不做 / 后续。
4. 业务流程：优先用流程图、泳道图或步骤表表达。
5. 功能说明。
6. 字段与状态。
7. 权限与异常。
8. 页面与交互。
9. 原型/实现同步项。
10. 验收标准。
11. 待确认问题。
12. 文档版本记录。

## 3. 字段、状态与 PRD

涉及字段、状态、权限时，必须写清：

- 字段名称、字段含义、类型、是否必填、默认值、来源、展示位置、编辑权限。
- 状态名称、状态含义、进入条件、退出条件、允许操作、异常回退、历史记录。
- 金额、时间、数量、库存、资源、账务、审批等关键规则的边界条件。
- 页面展示、接口传参、导入导出、日志记录、权限控制是否需要同步。
- 页面交互至少写页面目标、目标角色、入口、区块结构、字段/按钮、状态标签、弹窗、校验和异常提示。

字段不要只写中文名。需要进入真实实现时，再补 code、枚举、接口、数据表、兼容策略和迁移说明。

枚举 code 优先使用稳定的英文小写 `snake_case`；字段 code 遵循既有代码风格。

## 3.1 PRD 与原型最小对齐项

PRD 和原型不要各写各的。至少对齐下面几项：

1. 页面目标和页面入口。
2. 目标角色和权限差异。
3. 关键字段、按钮和行操作。
4. 状态、标签和可流转动作。
5. 弹窗、确认层、校验和异常提示。
6. 空态、失败态、禁用态、无权限态。
7. 本期不做和人工兜底项。

复杂后台页再额外写清：

- 主视图是什么：表格、卡片、地图、甘特、时间线还是控制台。
- 次级承载区是什么：抽屉、弹窗、右侧面板、标签页还是日志区。
- 摘要卡是纯展示，还是承担筛选/跳转入口。

如果用户明确说“先做原型页”，PRD 可以先写成精简页面说明，但不能缺上面这些关键项。

## 3.2 图表化表达

写业务文档、业务介绍、需求说明或 PRD 时，能用图表表达清楚的内容，默认优先用图表，不写成长段解释。目标是直观、简练、快速查阅。

优先图表类型：

| 内容 | 优先表达 |
| --- | --- |
| 业务流程、用户路径、审批链路 | 流程图或泳道图 |
| 状态生命周期、状态流转限制 | 状态图或状态流转表 |
| 角色、权限、可见/可操作范围 | 权限矩阵 |
| 字段、枚举、规则边界 | 表格 |
| 系统/模块/对象关系 | 结构图或关系图 |
| 规则分支、异常处理、人工兜底 | 决策树或异常流程图 |
| 排期、阶段、里程碑 | 时间线或路线图 |

使用规则：

1. PRD 的“业务流程”章节默认要有流程图或等价结构化图表，除非流程非常简单。
2. 关键状态超过 3 个时，默认补状态图或状态流转表。
3. 多角色协作、审批、交接、跨部门操作，优先用泳道图。
4. 字段、规则、权限、验收项优先用表格，不用散文段落堆说明。
5. 图表必须服务于决策和查阅，不为了装饰画图；图后只补必要说明。
6. Markdown 文档优先使用 Mermaid 或表格；PPT 优先使用可编辑图形、原生表格或母版中的图表页。
7. 如果工具或目标格式不支持可编辑图，说明限制，并保留一版可复制的文字/表格来源。

## 3.3 文档版本记录

正式 PRD 或其他文案类正式文件创建/修改时，必须保留文档自身版本记录。范围包括需求文档、方案说明、会议纪要、交接材料、客户说明、评审材料；PPT 的版本记录按 `32-方案PPT与模板.md` 执行。版本记录位置固定为标题/封面之后、正文之前；如果有目录，版本记录在目录之前。

版本记录至少包含：

- 版本号。
- 日期。
- 修改人。
- 修改内容。
- 依据或来源。

默认版本号：

- 新建正式文档：`V1.0`
- 小改：`V1.1`
- 范围、流程、字段、状态、权限发生明显变化：升一个中版本，如 `V1.2`
- 重大结构变化：按用户或组织规则处理。

不默认另外维护一份单独的“业务决策与变更记录”文件来代替文档自身版本记录；如果已有固定台账或版本制度，更新前必须确认。

## 4. 验收与测试

需求和 PRD 不能只写功能，要能验收。

验收标准至少覆盖：

1. 主流程成功。
2. 权限不允许时的表现。
3. 状态流转。
4. 字段校验。
5. 异常和边界。
6. 数据记录和历史追溯。
7. 页面展示和提示。
8. 与既有流程的兼容。

测试用例输出格式：

| 场景 | 前置条件 | 操作 | 预期结果 | 备注 |
| --- | --- | --- | --- | --- |

如果信息不足，先给验收框架和缺口，不要编造已确认规则。
