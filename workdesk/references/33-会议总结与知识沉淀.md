# 会议总结与知识沉淀

## 使用方式

Use this internal module for meeting notes, weekly/monthly summaries, review closeout, Obsidian capture, knowledge linking and reusable learning.

- Meeting notes, summaries or retrospectives: read sections 1 and 1.1.
- Obsidian capture and backlinking: read sections 2 to 2.1 only when the user explicitly asks to write, remember, backlink or store knowledge.
- Do not write Obsidian automatically. Propose path, summary and links first, then wait for confirmation.

## 目录

- `1. 会议纪要与工作总结`
- `1.1 日常工作交付标准`
- `2. Obsidian 知识沉淀`
- `2.0 经验抽象成方法论`

## 1. 会议纪要与工作总结

当输入明显是会议纪要、录音转写、周会内容或讨论记录时：

1. 先整理会议议题。
2. 再整理会议结果。
3. 标出未决问题、明确待办和责任方。
4. 区分“已确认结论”和“讨论中的想法”。
5. 只有可复用、能防错、能形成模板/检查清单，或用户明确要求记录时，才提示写入知识库。
6. 用户确认后，才写入 Obsidian、工作知识库、正式文档版本记录、PRD、Skill references 或其他文件。

会议讨论不能自动视为最终业务规则。只有用户明确确认的规则，才可进入正式资料、文档版本记录或知识库。

默认会议纪要结构：

1. 会议主题。
2. 时间与参与方。
3. 关键结论。
4. 讨论要点。
5. 待办事项：事项、负责人、时间、验收。
6. 未决问题。
7. 需要同步的资料。
8. 可沉淀经验。

需求变更后必须检查是否同步 PRD、原型、开发任务、测试用例、会议决议或知识库。涉及资金、权限、历史数据、账务、外部服务或上线范围时，不能只在聊天里确认，必须建议写回正式资料或文档版本记录。

周报、总结和复盘按时间、主题、结论、问题、下一步和可写入知识库的经验整理。

## 1.1 日常工作交付标准

默认输出要短、硬、可执行。不要用长解释替代结论。

| 场景 | 默认输出 |
| --- | --- |
| 普通问题 | 结论 + 影响点 + 下一步/待确认 |
| 资料恢复型问答 | 结论 + 依据阶段 + 依据文件/目录 + 不确定项 |
| 找文件 | 最可能文件 + 为什么匹配 + 下一步建议 |
| 找知识 | 相关知识点 + 来源位置 + 是否建议写入知识库 |
| 需求分析 | 结论 + 影响范围 + 漏洞/风险 + 推荐方案 + 待确认 |
| Review | 问题优先，按严重度列，附依据位置和修正建议 |
| 评审回应/整改 | 结论 + 依据资料 + 回应说明 + 整改动作 + 待确认 |
| 会议纪要 | 议题、结论、待办、责任方、时间、未决、知识记录建议 |
| 周报/月报 | 时间范围、完成事项、关键进展、问题风险、下步计划 |
| 方案/PPT | 受众目的、核心叙事、目录、关键页、资料缺口 |
| 收口/回写 | 本轮结论、已改/未改、同步项、知识记录项、下一步 |

除非用户要求“详细”“完整”“展开”，否则不要输出长篇流程说明。需要写文件时，先给将写内容和目标位置；确认后再落文件。

## 2. Obsidian 知识沉淀

本节只在用户明确说“记下来、写入知识库、存知识、双链、沉淀到 Obsidian”时展开。普通会议纪要、总结、复盘只在末尾用一句话提示是否值得沉淀。

`vault_root` must be discovered from the current workspace, an opened note path, or the user's confirmed target. Do not hardcode a personal absolute vault path in this reusable workflow.

默认流程：

1. 判断这条内容是否值得沉淀。
2. 判断写入类型。
3. 先检索已有知识，避免重复。
4. 给出建议路径、标题、摘要和双链。
5. 用户确认后再写入。

写入类型：

| 类型 | 用途 | 默认路径 |
| --- | --- | --- |
| 来源知识 | 某个工作来源中可复用、可追溯但不一定写入正式文档的知识 | 先查现有 Obsidian 目录；没有稳定目录时先问 |
| 个人通用知识 | 可复用的方法论、技巧、模板、原则和工具用法 | 方法论放 `知识库/个人能力成长/`；AI/Agent/Skill 放 `知识库/AI与Agent/`；工具用法放 `知识库/工具类/` |
| 工作笔记 | 会议、周报、日常工作主题的阶段性记录、分析过程、待办和复盘 | 先查现有目录；周报可用 `Workspace/工作月报/` |

值得写入知识库：

- 可跨场景复用的方法论。
- 反复出现的判断规则。
- 反复出现的 PRD / 原型 / 评审模板。
- 长期有效的业务规则速记。
- 踩坑复盘、检查清单、交付模板、命名规则、Prompt 模板。

不值得默认写入：

- 一次性聊天内容。
- 未确认事实。
- 临时偏好。
- 已否定且无复用价值的想法。
- 完整会议转写。
- 客户敏感信息、账号、密钥、合同价格等敏感内容。

新建或更新 Obsidian 知识笔记前必须确认。只有当用户明确要求“优化工作流/记规则/更新 Skill”时，低风险的 Skill 源库草案可以直接改；这不等同于可以自动写 Obsidian。

### 2.0 经验抽象成方法论

从具体来源写入个人能力库时，按四步处理：先记录来源事实；再识别是否是重复问题；然后提炼下次可复用的判断框架；最后建立双向链接。来源事实保留在来源资料或正式文档，通用方法才进入个人能力成长。

值得写入知识库的标准：不是一次性细节；能帮助下次更快写 PRD、做评审、验收或复盘；能形成检查清单、模板、判断规则或训练动作；能和现有笔记建立明确关系。

复杂需求完成后，默认轻量自问：最初遗漏了什么、为什么遗漏、最终补齐了哪些规则、属于哪类通用能力、下次类似问题先问什么、是否需要写入知识库。

## 2.1 关联知识与双链

记录新知识前，先检查仓库内是否已有相关知识，避免孤立笔记。

默认检索范围：

- `知识库/个人能力成长/`
- `知识库/AI与Agent/`
- `知识库/工具类/`
- 当前来源相关目录。
- `Workspace/`

检索策略：

1. 从新知识的来源、主题、关键词、同义词、方法名、工具名和交付物类型生成检索词。
2. 用 `rg` 搜标题、关键词和相关短语。
3. 先找可直接补充的旧笔记，再判断是否需要新建。
4. 如果已有笔记能承载，优先建议更新旧笔记，不新建孤立笔记。
5. 如果需要新建，给出建议双链。

输出给用户时先给：

1. 建议写入位置。
2. 建议标题。
3. 3 到 5 条摘要。
4. 建议关联的旧笔记。
5. 是否需要更新旧笔记的反链。

只有用户确认后，才实际写入。

双链规则：

- 新笔记的 `## 关联` 中使用 Obsidian wiki link：`[[笔记标题]]`。
- 如果新笔记强依赖旧笔记，同时建议在旧笔记 `## 关联` 中补回链。
- 已有笔记没有 `## 关联` 时，可在文末新增 `## 关联`；如果该笔记结构特殊或是正式资料，先问。
- 不确定关系时，只在建议中列出，不直接写。
- 候选过多、关系不确定或会修改正式资料时，先让用户选择，不自动写反链。

建议标题格式：

- 通用方法：`YYYY-MM-DD-主题-方法.md`
- 工具经验：`YYYY-MM-DD-工具名-问题.md`
- 工作复盘：`YYYY-MM-DD-主题-复盘.md`

写入建议模板：

```markdown
建议写入：

- 路径：
- 标题：
- 类型：
- 摘要：
  1.
  2.
  3.
- 建议双链：
  - [[已有笔记A]]
  - [[已有笔记B]]
- 是否需要回写旧笔记反链：
- 需要你确认：
```

知识笔记模板：

```markdown
# 标题

## 来源

- 日期：
- 来源：
- 材料：

## 结论

## 适用场景

## 方法 / 规则

## 注意事项

## 关联
```

来源知识必须标明来源和材料。个人通用知识必须标明适用场景，避免被误用成已确认事实。新知识必须检查已有相关笔记，并在 `## 关联` 中维护必要双链。
